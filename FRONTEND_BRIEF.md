ECHOASSIST — COMPLETE FRONTEND DESIGN & EXPERIENCE DIRECTION

The existing EchoAssist ML/inference system and API are already working.
Build the new user-facing frontend around that existing functionality.

This is a DESIGN-DRIVEN implementation request.

Do not make EchoAssist look like a generic AI, healthcare, SaaS, dashboard, or
startup-template website. The visual identity and interaction language must feel
original and specifically derived from acoustic analysis, sound, spectrograms,
clinical instrumentation, optical inspection, and signal interpretation.

Use the attached:
1. EchoAssist PS as the product/problem requirements.
2. EchoAssist technical thesis as the technical/product truth.
3. Final EchoAssist logo as the brand identity reference.
4. Color-palette reference as the palette relationship reference.

The attached visual references establish identity and aesthetic direction.
Do NOT copy their layouts literally.

==================================================
1. CORE CREATIVE DIRECTION
==================================================

The central visual idea of EchoAssist is:

SOUND → SIGNAL → VISUAL PATTERN → ANALYSIS → EXPLANATION → CONFIDENCE

The website should make this transformation feel physical and understandable.

The experience should feel like a sophisticated piece of clinical acoustic
technology rather than a conventional website.

Desired personality:

- premium
- minimal
- calm
- intelligent
- clinical without feeling sterile
- technically sophisticated
- human
- editorial
- tactile
- precise

It should feel expensive because of restraint, typography, spacing, motion,
materiality, and interaction design — NOT because it contains excessive effects.

Avoid anything that resembles a typical AI landing page.

==================================================
2. ABSOLUTELY AVOID GENERIC AI WEBSITE DESIGN
==================================================

DO NOT use the usual:

- glowing AI orb
- purple/blue gradient background
- generic neural-network graphics
- AI brain illustrations
- floating random particles
- stock doctors
- stock medical imagery
- giant rounded glass cards everywhere
- excessive pills/badges
- generic "AI-powered healthcare" hero
- meaningless animated blobs
- random 3D spheres
- excessive neon
- cyberpunk styling
- template-like feature cards
- excessive gradients
- generic dashboard aesthetics
- unnecessary rounded rectangles
- decorative graphics with no relationship to EchoAssist

If a visual could belong to 500 other AI startups, redesign it.

The design language must come from EchoAssist itself:
waveforms, acoustic signals, spectrograms, optical inspection, clinical
instrumentation, signal isolation, confidence, and explainability.

==================================================
4. TYPOGRAPHY
==================================================

Typography should feel editorial, modern, and highly intentional.

Use a strong contemporary sans-serif for major headlines and a highly readable
modern sans-serif for supporting text.

Prefer fonts that are readily available in the project's environment or can be
loaded efficiently.

Avoid:
- playful script fonts
- futuristic novelty fonts
- overly geometric "tech startup" fonts
- excessive font variation

Use large typography with generous whitespace.

Headlines should be confident and concise.

Supporting text should be restrained and readable.

Do not fill empty space just because it exists.

==================================================

of the website's motion language.

The waveform identity may subtly appear elsewhere in the experience, but never
as repetitive branding decoration.

The logo should remain clean and relatively small.

==================================================
6. ENTRANCE EXPERIENCE
==================================================

Create a short, smooth entrance/reveal sequence.

The entrance should feel like the interface is initializing/listening rather
than a cinematic loading screen.

Concept:

A minimal acoustic waveform/signal appears.

The waveform subtly resolves into the EchoAssist E identity.

The E settles.

The interface then reveals itself through a smooth optical/misty transition.

The hero content enters with restrained staggered motion.

The entire entrance should feel approximately 1–1.5 seconds and should NEVER
delay the user's access unnecessarily.

Do NOT use:
- loading percentages
- spinning loaders
- progress bars
- long logo animations
- particle explosions
- dramatic cinematic transitions

The entrance should transition naturally into the hero rather than feeling like
a separate animation before the website.

==================================================
7. HERO
==================================================

The hero should immediately establish:

EchoAssist
+
acoustic intelligence
+
clinical trust
+
sound becoming understandable.

Use large editorial typography and generous negative space.

The hero should NOT resemble a standard SaaS hero with:

==================================================
8. THE SIGNATURE REVOLVING INTERACTION
==================================================

This is one of the defining interactions of the website.

Create a scroll-driven spatial sequence resembling a revolving door WITHOUT
actually showing a door.

There is an invisible vertical axis.

Thin floating objects/panels are arranged around this invisible axis.

As the user scrolls, the objects rotate around the axis.

There should NOT be a visible circular carousel.
There should NOT be a visible door frame.
There should NOT be obvious mechanical hardware.

The user should feel as though they are moving through a physical system.

The currently active object rotates into the front-facing position.

Inactive objects recede into perspective and become more subtle, translucent,
and slightly softer.

The active object should be:
- crisp
- readable
- visually important

The peripheral objects should be:
- quieter
- translucent
- partially blurred where appropriate
- visually secondary

The rotation should be directly tied to scroll progress.

It must feel smooth and controlled, not like a PowerPoint 3D transition.

==================================================
9. WHAT THE ROTATING OBJECTS REPRESENT
==================================================

The objects are NOT random 3D decorations.

They represent the EchoAssist pipeline.

Use the conceptual progression:

01 — CAPTURE / LISTEN
02 — CLEAN
03 — ANALYZE
04 — EXPLAIN
05 — CONFIDENCE / TRUST

The objects should visually communicate these concepts through acoustic and
clinical abstractions.

Possible visual language:

CAPTURE:
a minimal acoustic sensing element / sound capture object

CLEAN:
a raw waveform becoming a cleaner signal

ANALYZE:
a spectrogram or acoustic-frequency structure

EXPLAIN:
a signal with a highlighted salient region

CONFIDENCE:
a restrained confidence indicator / analytical ring / probability structure

These should feel like physical design objects from the same visual system.

Do NOT use literal medical icons.

The objects should feel like abstract clinical instruments.

==================================================
10. MISTY OPTICAL GLASS
==================================================

Use glass as a MATERIAL, not as a UI trend.

The desired material is:

- translucent
- misty
- subtle
- optical
- slightly reflective
- softly blurred
- cool and clinical

The background should occasionally appear distorted/softened through the
material.

Do NOT create generic glassmorphism cards everywhere.

Do NOT put every section inside a glass rectangle.

Use the glass material primarily for:
- the revolving objects
- selected spatial UI elements
- the acoustic lens
- occasional key interaction surfaces

Glass should disappear when it doesn't need to be seen.

==================================================
11. FLOATING 3D OBJECTS
==================================================

Use floating 3D objects only where they reinforce the acoustic story.

Do NOT fill the page with 3D objects.

The floating objects belong primarily to the revolving interaction.

They should feel:
- lightweight
- precise
- abstract
- clinical
- tactile
- slightly futuristic but not sci-fi

Avoid generic spheres, blobs, crystals, planets, molecules, or random shapes.

Every 3D object should have a conceptual relationship to:
sound, signal, spectrogram, acoustic analysis, explanation, or confidence.

==================================================
12. ACOUSTIC LENS — SIGNATURE INTERACTION
==================================================

Create an interactive optical "acoustic lens."

This is one of the most important visual ideas in the website.

Show a waveform/spectrogram or acoustic visualization.

A translucent circular lens moves across the visualization.

Outside the lens:
the signal is relatively simplified and calm.

Inside the lens:
the acoustic structure becomes clearer and more detailed.

The lens should visually communicate:

LOOK CLOSER → UNDERSTAND THE SIGNAL

Use it to reveal meaningful acoustic regions.

Where appropriate, connect the lens to the model's salient region /
explainability result.

The interaction should make the user feel like they are physically inspecting
the sound.

This should NOT be a gimmicky magnifying glass.

It is an optical analysis instrument.

==================================================
13. "HEAR WHAT THE MODEL HEARD"
==================================================

Use the technical thesis concept of the salient second as a major storytelling
moment.

When the model identifies the region that contributed most strongly to its
prediction:

- visually isolate/highlight that region
- make the relationship between the signal and the explanation obvious
- provide an elegant audio interaction such as:
  "Hear what the model heard"

The visual and audio explanation should feel connected.

Do not present explainability as a generic percentage chart alone.

The user should understand:
THIS is the portion of the recording that influenced the result.

==================================================
14. PRODUCT / ANALYSIS EXPERIENCE
==================================================

The actual functional analysis experience must remain central.

The frontend should support the existing analysis functionality, including the
information already exposed by the inference layer.

Present results in a highly visual but clinically restrained manner.

Relevant information includes:
- predicted class
- confidence
- class probabilities
- signal quality
- cycles/segments where available
- spectrogram
- salient region
- explanation
- refusal state

Do not invent medical claims.

Do not transform a respiratory sound classification into a diagnosis.

Maintain the project's intended boundary:

The system analyzes acoustic patterns and supports interpretation.
It does not diagnose the patient.

==================================================
15. REFUSAL / LOW-QUALITY EXPERIENCE
==================================================

A refusal is NOT an error screen.

If the system determines that the recording is unusable or insufficiently
reliable, design a calm, intentional state.

Example conceptual message:

"No reliable signal detected."

Then explain what happened and what the user should do next.

The refusal state should feel like the system is responsibly saying:

"I don't have enough signal to give you a reliable result."

Never make refusal look like a broken application.

==================================================
16. TRUST / CONFIDENCE
==================================================

Confidence should be visually understandable without becoming a generic gauge
dashboard.

Use restrained visual language.

The user should understand:

- what the model predicted
- how confident it is
- what alternatives existed
- what evidence contributed to the result

Do not imply certainty where the model does not have it.

The visual hierarchy should emphasize informed interpretation rather than
"AI says this is definitely X."

==================================================
17. TECHNICAL STORYTELLING
==================================================

The website should naturally communicate the technical journey:

audio
→ preprocessing / cleaning
→ segmentation
→ spectrogram
→ acoustic features
→ classification
→ confidence
→ salient-region explanation
→ responsible output

Do not dump technical terminology into walls of text.

Turn technical concepts into visual experiences.

The thesis is the source of truth for technical claims.

Do not invent capabilities that do not exist.

==================================================
18. PERFORMANCE — HARD REQUIREMENT
==================================================

Performance is a FIRST-CLASS design constraint.

The website must remain usable on low-end laptops with limited RAM and
integrated graphics.

Do NOT assume a powerful GPU.

Do NOT use:
- unnecessarily large JavaScript bundles
- huge textures
- high-poly models
- video backgrounds
- continuous particle systems
- multiple simultaneous WebGL render loops
- unnecessarily expensive post-processing
- heavy animation running when elements are not visible

Prefer:
- CSS transforms
- SVG
- Canvas 2D
- GPU-composited opacity/transform animations
- lightweight DOM
- lazy-loaded assets
- efficient event handling
- viewport-aware animation
- reduced rendering when elements are not visible

Three-dimensional/WebGL effects should be progressive enhancements, not
requirements for the core experience.

If WebGL is unavailable or performance is poor, gracefully fall back to
lightweight CSS/SVG/Canvas equivalents while preserving the same visual
concept and hierarchy.

The site should still look intentionally designed in fallback mode.

Respect prefers-reduced-motion.

Pause/dispose expensive animation loops when elements are outside the viewport.

Do not trade usability for spectacle.

==================================================
19. RESPONSIVE DESIGN
==================================================

Design for:
- desktop
- laptop
- tablet
- mobile

The experience must not simply shrink.

The revolving interaction should have an intelligent mobile equivalent.

If a 3D spatial interaction becomes inappropriate on a small screen, transform
the same concept into a lightweight sequential interaction while preserving
the meaning.

Do not force tiny 3D objects onto mobile screens.

Typography, spacing, interaction targets, and content hierarchy must remain
excellent at every size.

==================================================
20. MOTION LANGUAGE
==================================================

- smooth
- physical
- deliberate
- slightly slow
- precise
- continuous

Avoid:
- bouncing
- excessive springiness
- random floating
- flashy entrance effects
- constant movement

Every major animation should answer:
"Why is this moving?"

Examples:

waveform forming → identity

rotation → moving through the analysis pipeline

lens movement → inspecting acoustic detail

highlight → model explanation

confidence transition → understanding uncertainty

==================================================
24. OVERALL QUALITY BAR
==================================================

The final result should feel like a real premium clinical technology product,
not a hackathon template.

It should be immediately recognizable as EchoAssist even without seeing the
logo.

The strongest qualities should be:

1. distinctive visual identity
2. excellent typography and whitespace
3. acoustic/signal-driven visual language
4. restrained optical glass
5. meaningful spatial interaction
6. memorable entrance
7. excellent explainability presentation
8. responsive behavior
9. low-end performance
10. technical credibility

The website should feel sophisticated without feeling overdesigned.

If an effect does not improve the story, remove it.

If a 3D object is only there because it looks cool, remove it.

If a section feels like a generic AI landing page, redesign it.

If an interaction compromises performance, simplify it.

If a visual conflicts with the actual product behavior described in the PS or
technical thesis, prioritize the actual product.

The goal is not to make the most complicated website.

The goal is to make the most memorable, coherent, technically honest,
high-quality EchoAssist experience possible.
